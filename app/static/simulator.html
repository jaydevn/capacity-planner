900s buffer · 3/15 breaches · 10% bandAWS defaultsNot customer-specific. Pre-launch buffer ≥ instance warm-up (~700–750s); scale-out ~3×1-min, scale-in ~15×1-min with a ~10% deadband — documented AWS behavior.
Modeled per AWS docs: Predictive scaling generates an hourly forecast for the next 48 h (refreshed every 6 h) and sets predicted capacity at the start of each hour, optionally pre-launching by SchedulingBufferTime (900 s here); it scales OUT only. Target tracking creates two managed CloudWatch alarms — a High alarm (scale-out, ~3×1-min breach) and a Low alarm (scale-in, ~15×1-min breach, ~10% band); warming instances are excluded from the metric and block scale-in; no scaling on insufficient data. When both run, desired = clamp( max(predicted, target-tracking), min, max ) — the HIGHER value always wins, so predictive acts as a floor that blocks target-tracking scale-in below the plan (predictive never scales in). Target-tracking scale-in is conservative: it removes capacity only past a ~10% deadband, never so much that the metric would rise back above target ("won't remove a unit if it would breach"), and one step per cooldown (~900 s) — so capacity steps down gradually instead of dropping to a single computed number.
